# SLSA Build Level 3 Reusable Attestation Workflow

## Overview

The `slsa-build-attest.yml` reusable GitHub Actions workflow provides a standardized, hardened pipeline for building container images and generating non-falsifiable cryptographic build provenance satisfying **SLSA (Supply-chain Levels for Software Artifacts) Build Level 3**.

By delegating container builds and provenance generation to this centralized workflow, application repositories across the `oss-slu` organization ensure that their distributable artifacts are built in clean, isolated environments and can be cryptographically verified prior to deployment on our Kubernetes cluster.

---

## Why SLSA Build Level 3?

SLSA Build Level 3 addresses critical threats in the software supply chain:

1. **Isolated & Ephemeral Build Environment:** Builds execute exclusively on freshly provisioned, ephemeral GitHub-hosted runners (`ubuntu-latest`). Unlike long-lived or shared cluster nodes, ephemeral runners eliminate artifact contamination, cross-build leakage, and unauthorized local modifications.
2. **Service-Generated Provenance:** The provenance statement is generated by the GitHub Actions runner platform itself, not by user-controlled build scripts.
3. **Non-Falsifiability:** The attestation envelope is cryptographically signed using Sigstore Fulcio with an OIDC workload identity issued by GitHub. Build steps inside the container cannot access or tamper with signing certificates or keys.
4. **Digest-Level Immutability:** Workloads reference container images by immutable SHA256 content digests (`image@sha256:...`) rather than mutable branch/floating tags (`:latest`).

## Workflow Inputs & Outputs

### Inputs

| Parameter | Type | Required | Default | Description |
|---|---|---|---|---|
| `image-name` | `string` | **Yes** | — | Fully qualified container image name (e.g., `ghcr.io/oss-slu/oss_dev_analytics`). |
| `harbor-image` | `string` | No | `""` | Optional target image name on on-prem Harbor registry (e.g. `registry.oss-slu.online/repoexplorer/app`). |
| `harbor-registry` | `string` | No | `registry.oss-slu.online` | On-prem Harbor container registry host. |
| `report-harbor-scan` | `boolean` | No | `true` | Whether to poll Harbor Trivy scan API and report results in GitHub Actions Step Summary. |
| `context` | `string` | No | `.` | Docker build context directory. |
| `file` | `string` | No | `Dockerfile` | Path to Dockerfile relative to context. |
| `target` | `string` | No | `""` | Target build stage for multi-stage Dockerfiles. |
| `build-args` | `string` | No | `""` | Multiline string of build-time arguments (`ARG_NAME=val`). |
| `platforms` | `string` | No | `linux/amd64` | Target CPU architectures for Docker Buildx. |
| `push` | `boolean` | No | `true` | Whether to push the built image to the container registry. |
| `runner` | `string` | No | `ubuntu-latest` | GitHub runner OS. Must remain a GitHub-hosted runner to preserve SLSA L3 isolation. |
| `registry` | `string` | No | `ghcr.io` | Target container registry. |
| `tags` | `string` | No | `""` | Additional multiline tag specifications for `docker/metadata-action`. |
| `generate-sbom` | `boolean` | No | `true` | Whether to generate an SPDX Software Bill of Materials (SBOM) using Anchore Syft. |
| `sbom-format` | `string` | No | `spdx-json` | SBOM specification format (`spdx-json`, `cyclonedx-json`). |
| `sbom-artifact-name` | `string` | No | `""` | Custom name for the uploaded SBOM workflow artifact. |
| `attest-provenance` | `boolean` | No | `true` | Whether to attest SLSA Build Level 3 provenance. |
| `attest-sbom` | `boolean` | No | `true` | Whether to cryptographically attest the generated SBOM bound to the container image digest. |

### Secrets

| Secret | Required | Description |
|---|---|---|
| `HARBOR_ROBOT_USERNAME` | No | Push robot username for on-prem Harbor registry (e.g. `robot$repoexplorer+push`). Passed via `secrets: inherit`. |
| `HARBOR_ROBOT_PASSWORD` | No | Push robot secret token for on-prem Harbor registry. Passed via `secrets: inherit`. |

### Outputs

| Output | Description |
|---|---|
| `image-digest` | Immutable SHA256 digest of the built image (e.g., `sha256:7b1e...`). |
| `image-ref` | Full canonical image reference including digest (`ghcr.io/oss-slu/app@sha256:...`). |
| `harbor-image-ref` | Full canonical Harbor image reference including digest (`registry.oss-slu.online/app@sha256:...`). |
| `attestation-url` | Web URL to the GitHub-hosted cryptographic attestation summary. |
| `sbom-attestation-url` | Web URL to the GitHub-hosted cryptographic SBOM attestation summary. |
| `sbom-digest` | SHA256 content digest of the generated SBOM JSON document. |
| `harbor-scan-severity` | Overall severity from Harbor's automated Trivy scan (`Critical`, `High`, `Medium`, `Low`). |
| `harbor-scan-total` | Total vulnerability count detected by Harbor's Trivy scanner. |

## Consumer Usage Example

To adopt this workflow in your project repository (e.g. `oss_dev_analytics`), create or update `.github/workflows/build-and-deploy.yml`:

```yaml
name: Build & Deploy Container

on:
  push:
    branches: [main, staging]
    tags: ['v*']
  pull_request:
    branches: [main]

permissions:
  contents: read
  packages: write
  id-token: write
  attestations: write

jobs:
  build-container:
    # Reference the reusable workflow from oss_cicd_automation
    uses: oss-slu/oss_cicd_automation/.github/workflows/slsa-build-attest.yml@main
    with:
      image-name: ghcr.io/${{ github.repository_owner }}/oss_dev_analytics
      context: .
      file: Dockerfile
      push: ${{ github.event_name != 'pull_request' }}
    secrets: inherit

  deploy-staging:
    needs: [build-container]
    if: github.ref == 'refs/heads/staging' && github.event_name == 'push'
    runs-on: ubuntu-latest
    steps:
      - name: Deploy to Cluster via GitOps
        run: |
          echo "Deploying verified image: ${{ needs.build-container.outputs.image-ref }}"
          # Trigger ArgoCD sync or update k8s-manifests repository with image-digest
```

> **Note on Permissions:** The calling workflow **must** declare `id-token: write` and `attestations: write` so that GitHub Actions can issue the OIDC identity token and register the Sigstore provenance envelope.

## Verifying Attestations Locally and in CI

Attestations published by this workflow can be verified independently by any consumer, cluster webhook, or security auditor using the GitHub CLI:

```bash
# Verify provenance for a published container image:
gh attestation verify oci://ghcr.io/oss-slu/oss_dev_analytics:<sha> \
  --owner oss-slu
```

Expected verification output:
```text
Loaded digest sha256:... for oci://ghcr.io/oss-slu/oss_dev_analytics:...
Loaded 1 attestation from GitHub API
✓ Verification succeeded!

[SLSA v1.0 Provenance]
  Build definition:
    Build type: https://actions.github.com/buildtypes/v1/run
    Source repository: oss-slu/oss_dev_analytics
    Workflow: .github/workflows/build-and-deploy.yml
  Signer:
    Certificate identity: https://github.com/oss-slu/oss_dev_analytics/.github/workflows/build-and-deploy.yml@refs/heads/main
    Certificate issuer: https://token.actions.github.com
```

## Integration with Cluster Admission (Kyverno / Policy Controller)

Cluster operators can configure admission webhooks on the Kubernetes cluster (`oss_infra_ops`) to verify that all deployed pods run images signed by the `oss-slu` GitHub organization:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: verify-slsa-attestation
spec:
  validationFailureAction: Audit # Set to Enforce once all workloads migrate
  rules:
    - name: verify-ghcr-attestation
      match:
        any:
          - resources:
              kinds: [Pod]
      verifyImages:
        - imageReferences: ["ghcr.io/oss-slu/*"]
          attestations:
            - predicateType: https://slsa.dev/provenance/v1
              attestors:
                - entries:
                    - certificates:
                        issuer: https://token.actions.github.com
```
